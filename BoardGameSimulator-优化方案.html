2 CSS 设计系统差距 高优先

2.1 当前问题

BoardGameSimulator 的 styles.css 现状：

  • 124 行，所有样式堆在一个文件里
  • 选择器全部是全局的（.card-hand、.btn），无命名空间隔离
  • 颜色值直接写死在 CSS 中，无主题切换能力
  • 无 SCSS — 没有 mixin、function、变量继承
  • 硬编码的数值散落各处（width:46px、font-size:13px）

2.2 参考 AW-2025-Portfolio 的 SCSS 架构

层AW 的做法给 BGS 的建设
变量层 variables-scss/_colors.scss 定义 $theme-colors map（两组主题） 把现有 CSS 变量提取到 src/styles/_tokens.scss，定义完整 token 体系
CSS 变量生成 variables-css/_colors.scss 编译生成 :root { --color-primary: ... } 已有 :root（8 个变量），这是好的开始，应扩展为 token 体系
Helper 函数 color(key) 返回 var(--color-xxx)；ease(key) 返回 cubic-bezier；t(key) 一键排版 引入 SCSS，创建 color()、spacing()、font() 等函数
响应式 mq($bp) mixin 统一断点管理 把 @media(min-width:401px) 替换为 @include mq(desktop)
弹性布局 flex(row, center, space-between) 封装 flex 写法 创建 @mixin flex($dir, $align, $justify) 减少样板

2.3 具体建议：引入 SCSS 设计系统

// 新建 src/styles/_tokens.scss
$colors: (
  bg:      #ffffff,
  bg2:     #f2f2f7,
  label:   #000000,
  blue:    #0088ff,
  red:     #ff383c,
  green:   #34c759,
);

$ease: (
  out:    cubic-bezier(0.25, 0.46, 0.45, 0.94),
  in-out: cubic-bezier(0.42, 0, 0.58, 1),
);

$breakpoints: (
  desktop: 401px,
);

// 新建 src/styles/_mixins.scss
@mixin flex($dir: row, $align: stretch, $justify: flex-start) {
  display: flex;
  flex-direction: $dir;
  align-items: $align;
  justify-content: $justify;
}

@mixin mq($bp) {
  @media (min-width: map.get($breakpoints, $bp)) { @content; }
}
收益：引入 SCSS 后，所有颜色、间距、字号都有单一来源（single source of truth）。未来要加暗色主题，只需要在 tokens 层加一组配置，无需改任何组件代码。

3.3 Web Component 模式

参考 AW 中的 <a-work> 自定义元素：

// 推荐：BoardGameSimulator 中的核心 UI 元素可以用 Web Component 封装
class GameCard extends HTMLElement {
  static observedAttributes = ['suit', 'rank', 'selected'];

  connectedCallback() { this.render(); }
  attributeChangedCallback(name, _, val) {
    if (name === 'selected') this.classList.toggle('is-selected', val === 'true');
  }
  render() {
    this.innerHTML = `<span class="card-face">${this.getAttribute('name')}</span>`;
  }
}
customElements.define('game-card', GameCard);
// 使用: <game-card suit="heart" rank="A" name="♥A"></game-card>

这样做的好处：

  • 每张牌的状态自成一体，不依赖全局选择器
  • selected 状态通过 observedAttributes 触发 CSS class 切换，逻辑内聚
  • 可以单独测试 GameCard 组件

4 事件驱动架构提升 中优先

4.1 当前问题：回调地狱

// main.ts 当前的通信方式：renderer 通过回调向 main 报告事件
renderer.init({
  onImportGame: async () => { ... },
  onCreateRoom: async (gameId) => { ... },
  onJoinRoom:    async (qrData) => { ... },
  onStartGame:   () => { ... },
  onPlayAction:  (type, payload) => { ... },
  onLeaveRoom:   () => { ... },
  // ... 共 12 个回调，全部定义在 init() 的一个对象参数里
});

这种模式的本质问题：main.ts 成了上帝文件，所有逻辑都要在这里定义。新增一个界面行为，就要在 init 对象里加一个回调，main.ts 会不断膨胀。

4.2 参考 AW 的 Emitter 事件总线

// AW-2025-Portfolio 的做法：全局事件总线，完全解耦
import Emitter from '../utils/Emitter';

// 任何组件都可以随时发布事件
Emitter.emit('tick', time);
Emitter.emit('resize', widthChanged, heightChanged);
Emitter.emit('mousemove', clientX, clientY);

// 任何组件都可以随时订阅事件（自主决定何时绑定/解绑）
Emitter.on('tick', this.tick, this);
Emitter.on('resize', this.onResize, this);
Emitter.off('tick', this.tick, this);  // 组件销毁时解绑

4.3 给 BGS 的事件总线方案

// 新建 src/utils/EventBus.ts
class EventBus {
  #events = new Map();

  on(name: string, fn: (...args: any[]) => void, ctx?: any) {
    if (!this.#events.has(name)) this.#events.set(name, []);
    this.#events.get(name)!.push({ fn, ctx });
  }

  off(name: string, fn: (...args: any[]) => void) {
    const list = this.#events.get(name);
    if (list) this.#events.set(name, list.filter(e => e.fn !== fn));
  }

  emit(name: string, ...args: any[]) {
    this.#events.get(name)?.forEach(e => e.fn.apply(e.ctx, args));
  }
}

export const bus = new EventBus();

改用事件总线后：

  • renderer 只需要 bus.emit('ui:play-cards', cards)
  • engine 只需要 bus.on('ui:play-cards', handlePlay)
  • 两者完全不知道对方的存在，由总线中介
  • 新增功能只需订阅新事件，不需要改已有代码

5 动画系统升级 中优先

5.1 当前状态

BoardGameSimulator 使用 motion 库（12.42.2 版本，100KB+）但只用于非常基础的过渡动画。当前动画效果：卡片选中时 transform: translateY(-12px)，按钮按下缩放 0.97。

5.2 AW 的动画体系对比

动画能力AW-2025-PortfolioBGS 当前
入场动画GSAP Timeline，多阶段协调无系统性入场动画
滚动驱动ScrollTrigger，随滚动进度变化不适用（无滚动）
逐帧动画Ticker + requestAnimationFrame无（但扫描器用 RAF 跑检测）
缓动函数28 种 cubic-bezier，统一管理cubic-bezier(.25,.1,.25,1) 硬编码
过渡动画CSS transition + GSAPCSS transition（仅几处）

5.3 建议：提升棋牌类动画体验

桌游场景下的动画增强方向：

  1. 发牌动画：牌从牌堆"飞"到每个玩家手中。用 GSAP stagger 可以轻松做到 54 张牌依次飞出
  2. 出牌动画：打出的牌从手牌位平滑移动到桌面中央，带微小的旋转 shake
  3. 叫地主动画：底牌翻转亮牌效果（rotateY + backface-visibility）
  4. 炸弹特效：打出炸弹时全屏震动 + 粒子爆炸（Canvas）
  5. 胜利动画：获胜时手牌飞出散落，金色粒子上升
  6. 页面切换：首页→房间→游戏的过渡应加入 smooth page transition
考虑替换 motion 为 GSAP：motion 库 100KB+ 但只用到了 animate() 函数。GSAP 的 gsap core 只有 ~30KB，且提供更丰富的动画控制（Timeline、stagger、yoyo、repeat）。如果未来要加复杂动画，GSAP 是更优选择。不过 motion 也可保留——两个库关注点不同。

6 性能优化模式 中优先

6.1 AW 中的三个核心优化模式

优化模式AW 实现BGS 可借鉴点
1. IntersectionObserver + tick 暂停 所有动画组件在离开视口时取消 tick 订阅，完全停止运算 扫描器（startScanner）在用户离开页面或切换到后台时应该暂停 RAF 循环
2. will-change 提示 GPU 层 每个动画元素的 CSS 都声明 will-change: transform 给 drawer、main-stage、card-hand.sel 添加 will-change 提示
3. content-visibility 延迟渲染 AWork 组件用 content-visibility: hidden 阻止离屏视频渲染 抽屉中的游戏列表如果超过 20 个，可用此属性延迟渲染不可见项

7.2 innerHTML 字符串拼接 vs 声明式模板

// BGS renderer.ts 当前：用 innerHTML 拼 60 行字符串
this.el.innerHTML = `<div class="main-stage">
  <section class="home-sec">
    <input type="file" id="load-input" ...>
    <button id="btn-load">📂</button>
    ...
    ${games.map(g => `<div class="cell">...</div>`).join('')}
  </section>
</div>`;
// 然后马上用 getElementById 把元素抓回来绑定事件...
const stage = document.getElementById('main-stage')!;
const drawer = document.getElementById('drawer')!;
问题：innerHTML + getElementById 的组合是极其脆弱的方式。任何 ID 拼写错误都会在运行时静默失败（返回 null → 解引用报错）。而且 innerHTML 销毁原有 DOM 再重建，意味着所有事件监听器丢失、状态重置。

建议替代方案：

// 方案 A：使用 createElement（比 innerHTML 更安全）
private createHomeView(): HTMLElement {
  const stage = document.createElement('div');
  stage.className = 'main-stage';
  
  const input = document.createElement('input');
  input.type = 'file';
  input.addEventListener('change', this.onFileSelected);
  
  const button = document.createElement('button');
  button.textContent = '📂';
  button.addEventListener('pointerdown', () => input.click());
  
  stage.append(input, button);
  return stage;  // 直接返回带事件绑定的 DOM
}

// 方案 B：使用 lit-html 等轻量模板库（~3KB）
// 方案 C：引入 Astro / Svelte 等编译时框架

9 L1/L2/L3 架构与参考项目的异同

BoardGameSimulator 的三层架构是其最大亮点：

层内容评价
L1 Data卡牌定义、玩家数、UI 布局描述、可视性规则优秀 — JSON 驱动，游戏规则完全可配置
L2 Behavior行为规则（触发条件 + 动作序列），由 engine 执行优秀 — 声明式规则引擎雏形
L3 LogicWeb Worker 沙箱中的自定义 JS 脚本（如斗地主牌型检测）优秀 — 安全隔离，支持热加载

这个架构与 AW-2025-Portfolio 没有直接对应关系（AW 是展示型网站，不需要规则引擎），但 L1/L2/L3 的分层思想本身是架构教科书级别的设计，应继续深化。

AW 值得借鉴的地方在于：把这套架构也用到 UI 层：

  • L1 中已有 uiLayout 和 UISlotConfig 的类型定义，但实际 UI 渲染并未读取这些配置
  • 应让 Renderer 读取 L1 中的 uiLayout，动态渲染界面——这样不同游戏可以用不同 UI 布局

10 整体架构改进方向

10.1 当前架构分析

     main.ts（胶水代码）
        /    |    \
   p2p.ts  engine.ts  renderer.ts
   (P2P)   (游戏逻辑)  (UI渲染，417行)

这是一个 星型依赖 结构：main.ts 依赖所有模块，所有模块也通过回调依赖 main.ts。这是典型的初版 MVP 架构——快速但难以扩展。

10.2 建议的目标架构（以 AW 为参考）

                   EventBus（事件总线）
                 /    /    |    \    \
    GameEngine  P2PManager  Router  ViewComponents
    (不变)       (不变)      (新增)   (拆分自renderer)

     ┌─ HomeView       ─┐
     ├─ LobbyView      ─┤
     ├─ GameView       ─┤  ← 每个视图独立文件
     ├─ CardComponent  ─┤     template + script + style
     ├─ ScannerView    ─┤
     └─ ToastView      ─┘

10.3 渐进迁移路径

  1. 阶段 1（不改架构）：引入 SCSS + tokens 文件 → 统一颜色/间距管理 → 不影响运行时逻辑
  2. 阶段 2（轻量重构）：创建 EventBus → 替换 main.ts 中的回调为事件 → 不改 UI 渲染方式
  3. 阶段 3（视图拆分）：从 renderer.ts 中逐块抽出独立视图类 → 每个视图只负责一种界面
  4. 阶段 4（可选）：引入 Astro / Svelte 等框架 → 声明式模板替代 innerHTML → 最大的改造成本

10.4 是否引入框架？

🔴 保持纯 TypeScript

优点：零依赖、打包小、无学习成本

缺点：UI 代码量线性增长、无声明式模板、状态同步手动处理

🟢 引入 Astro / Svelte

优点：声明式模板、组件隔离、内置 SCSS 支持、构建优化

缺点：学习成本、增加构建复杂度、框架版本升级维护

建议：对于 BGS 这种交互密集型应用，Svelte（不是 Astro） 可能是更好的选择。Svelte 编译后无运行时、体积小（~2KB）、响应式系统天然适合游戏 UI 状态更新。Astro 更适合内容型网站（如 AW-2025-Portfolio）。

总结

核心结论

BoardGameSimulator 在架构设计（L1/L2/L3、Core/Client 分离、Registry 模式、P2P 方案）和工程实践（测试、类型定义、issue 追踪）上已经达到甚至超过了 AW-2025-Portfolio 的水平。

差距集中在前端 UI 工程化方面：缺乏设计系统（SCSS tokens）、缺乏组件化（renderer.ts 是 God Object）、缺乏声明式模板（innerHTML 字符串拼接）、缺乏系统性的动画设计。

这些差距不是能力问题，而是阶段问题——BGS 是一个技术探索型项目（"能不能用 QR 传 WebRTC SDP？"），UI 是事后补的。当项目从 MVP 阶段走向成品阶段时，上述所有优化点都会变得必要。
